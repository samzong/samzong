# Lody Duo delegation

## Single-layer Deep and Fast delegation

Build Standard is the development lead. Research Deep is the investigation lead. This file calls both of them leads. Build Standard can consult Architect, delegate to Build Fast, and open module Build Standard sessions under "Parallel modules". A module Build Standard cannot open another Build Standard. Research Deep delegates only to Research Fast. Architect, Review, Fast, and Ops never delegate. When the host dispatches a lead, it grants these bounded delegation rights. A lead follows the dispatch, working directory, async execution, and recovery rules of SKILL.md. Before dispatch, a lead reads the actual role ID from the catalog.

Lody has two kinds of relationship. A Tab (`useCurrentSessionAsParent:true`) belongs to the session that created it and shares that session's working directory. A Tab cannot open another Tab. An opened session (explicit `workContext`) is independent and has its own working directory. The host opens a lead as an independent session with `workContext`, not as a Tab. A lead can open a same-directory Fast or a read-only Architect adviser as its own Tab. Those Tabs cannot recruit partners. When you create a Tab, always pass `useCurrentSessionAsParent:true` explicitly, and confirm that the new session inherited the expected project. Do not rely on the default. Use `workContext` to open an independent session only when the partner needs another directory, and state the verified actual directory in the assignment. An independent session for a project task, including Review and Ops, must bind to a local project or GitHub repository that the catalog verified. An independent session is not a chat, and a new context does not mean no project. Verify the project binding and the actual working directory separately. Point to the target `gmc` worktree with an absolute path and `git -C`. Do not create another worktree with `worktree:true`. Use `workContext:{kind:"chat"}` only for a task that really has no project. To continue the same subtask or the same design question, use `lody_session_chat` in the original partner session. After dispatch, if no independent work remains, end the current turn. A completion notice reaches a lead only when it has no active turn, so a wait inside a turn delays the notice. When the user mentions a role with @, Lody only rewrites this into an instruction to create a session with that role. It does not set the relationship.

- A completion notice returns only the turn that was dispatched. Suppose a lead ends its turn to wait for partners. Its report then starts with the literal text `进行中` ("in progress") and lists the partners that are not finished. This report is not a delivery. The dispatcher records it and ends its turn. The dispatcher does not poll and does not push. A turn that follows a partner result is started by the system and is not blocked by REVERSE_CHAT_FORBIDDEN. The dispatcher writes its own session ID (environment variable `LODY_SESSION_ID`) in the dispatch message. In the turn where the lead finishes integration and verification, the lead uses one `lody_session_chat` call to send the final evidence packet to that session. A dispatcher cannot chat back to the lead within the turn that this message started. First start work that does not depend on the lead, for example a Review, and end the turn with a result that starts with `进行中`. When that work finishes, continue the lead in the next turn. If there is no such work, end the turn with the correction or instruction as its result, and the result returns to the lead automatically. When a lead receives a turn result from the dispatcher that starts with `进行中`, it only records the result and ends its turn. If the result does not start with `进行中`, the correction or instruction in it is a new instruction for this task, and the lead must follow it. The "reference material" header that Lody adds to automatic results does not change this. Creating a session, dispatching by chat, and each automatic return each add 1 to the call chain depth. At depth 16, Lody drops the wake-up without an error. If a final evidence packet is sent back for correction more than 2 times, the host stops the exchange and reports the remaining work and the reason to the user.
- Fast receives only tasks with a clear goal, scope, settled approach, and acceptance conditions. Research Deep gives useful searches, locating, and fact checks to Research Fast. Build Standard delegates to Build Fast within the boundaries in the section "Build Standard's development responsibility and design consultation" of SKILL.md. The lead clarifies anything that is not yet clear before it dispatches. Do not send unclear work to Fast to try out.
- The number of Fast partners is not limited. Research Fast is read-only and can run in parallel, one per question. For Build Fast, each worktree still has one writer. Dispatch sequentially in the same worktree. If parallel work is needed, Build Standard first creates a separate worktree for each Fast with `gmc` and owns the integration.
- Each assignment gives the goal, the input version, the working directory in the actual environment of the Fast, the unique write scope, the settled approach, the acceptance commands, and a report format of about 20 lines or less. The report must include the commands that were actually executed and their key output. Treat a conclusion without execution evidence as unfinished. The authority that you delegate must not exceed the authority that you hold. Fast does not commit, push, or open a PR. The exception is a local commit in its own isolated worktree, when the lead explicitly asks for it.
- The lead does not trust the statements of a Fast. The lead reruns the checks that decide the conclusion. Lody session history does not contain tool calls, so the commands and outputs in a report are only leads. A conclusion such as "not found", "cannot access", or "no tools" also needs execution evidence. Without evidence, treat the task as unfinished, and dispatch again or finish it yourself. Verify each diff and each cited location. The reasoning effort of a Fast role must be at least `high`. We measured that Luna at `low` states facts without calling any tool. When a Fast reports that the task is beyond its ability, the original lead takes over. Build Standard decides itself whether a design consultation is needed. It does not hand the task to Architect automatically.
- The lead's report lists a Markdown session link for each partner, in the format [@Title](lody://session/SESSION_ID?workspace=WORKSPACE_ID). Take the workspace value from a lody:// link that already exists in the conversation. If there is no such link, leave out the workspace query parameter. Never put a link in backticks or a code block. The report also lists the operationId and the verification conclusion. For a consultation, state which advice was adopted or rejected and why. The lead follows [Partner archiving](#partner-archiving) for the time of archiving and the report. The host spot-checks this list. It checks for delegation beyond the allowed levels, write conflicts, unverified Fast results, and an adviser that is presented as an independent reviewer.

## Recovery rules

- After a lost response, an error, a timeout, or a host recovery, first verify the original request, the queue, the target turn, and the side effects. Use `lody_operation_get` and `lody_operation_list`, `lody_session_status_many`, and when needed `lody_session_history`. Do not dispatch again before you verify. Errors from `lody_session_create` or `lody_session_chat`, for example `SYNC_UNAVAILABLE`, do not prove that Lody did not accept the request. An Operation error `TARGET_TIMEOUT` does not prove that the target turn failed. Read the target state and history, and if there is a reply, accept the actual reply. Page through the history only as needed and avoid exports of unrelated content.
- Suppose a Lody tool returns `INTERNAL_ERROR` (for example, `Workspace cleanup failed`) and `lody_session_create_options` returns the same error. The Lody MCP host is then blocked until Lody restarts, and `retryable` does not apply. Check each partner that you already dispatched with `lody_operation_get`, and do not dispatch it again. Report the error unchanged, and let the user decide when to restart Lody.
- To recover an accepted create, use the original `operationId` and `resume:true`. Do not send the prompt again. A chat has no `resume` field. Follow its identity and recovery contract.
- A timeout, a successful cancel request, an offline machine, or no output does not prove that the partner stopped. After a cancel, confirm that execution ended, that no related turn is queued, and that the write results are verified. Only then resend or take over the same write scope. Without that evidence, keep the uncertainty and continue work that does not depend on it.
- When a completion notification is late or duplicated, reconcile the records and reuse the accepted result. Do not restart a goal that is complete.

## Continuation and cancellation

The cancellation rule below is the cancellation item in the [recovery rules](#recovery-rules).

- Suppose a partner turn is running and new input arrives. First decide whether the input adds to the turn or withdraws part of it. An addition only adds information or tasks and does not change the actions of the running turn. Do not cancel. Queue it as a continuation with a new `operationId`, and write that it adds to the previous message and that the original instruction is unchanged. A withdrawal or narrowing changes an external action in the running turn (push, publish, merge, close, comment, external write). In this case, first cancel the running turn with `lody_operation_cancel`. Confirm as the cancellation rule requires that the turn stopped, and verify the side effects that already happened. Then send one self-contained replacement instruction. It states that this message takes precedence and replaces `<operationId>`. It repeats the parts of the original instruction that are still valid, adds the withdrawals and additions, and handles side effects that already happened and do not roll back automatically. Never queue only the withdrawal message behind the running turn.

## Partner archiving

The host and the leads (Build Standard, Research Deep) archive the partners that they opened and no longer need. The one who opened a partner with `lody_session_create` (including batch creation) calls `lody_session_archive` after acceptance. Never archive your own session, the session that opened you, or the user's top-level session. When Research Deep archives the partners that it opened, this section authorizes it. This does not change the read-only boundary of its investigation work.

- Before archiving, use `lody_session_status_many` to confirm that the target has `executionState=idle` and `queuedTurnCount=0`, that its result is accepted and integrated, and that the opener plans no continuation. First handle the partners that the target opened, and confirm that all of them ended. Then archive from the bottom up. Do not archive a running partner as a way to clean up. Pending Operation Deliveries on an archived session stay pending until a person restores the session. Archiving does not replace receiving and accepting the result.
- `lody_session_archive` is idempotent, and you can restore an archived session in Lody. Archiving also archives the Tabs that the target contains (`parentSessionId`). It does not archive the independent sessions that the target opened with `workContext` (they have only `openedBySessionId`). Do not treat the archiving of a lead as proof that its independent partners are archived.
- Keep a partner when you wait for a user answer and then continue with the same partner, or when you still need it for UI iterations, external PR review, a merge, or review comments. In the report, list `保留：<会话链接> — 原因` (kept: session link, reason). The times in the table below apply only when the conditions above are met. Do not archive early only because a phase is reached.
- For Review, Research Deep, Ops, and a Build Standard that is not a module, the table gives the earliest time at which the host can archive. The host does not have to archive at each phase. Before the final report, the host can use one `lody_session_status_many` call to query all partners it opened, and then call `lody_session_archive` in parallel for the partners that meet the conditions. This reduces the host's context. A lead (Build Standard or Research Deep) still archives the partners it opened before it returns the final evidence packet. A module session is archived according to step 6 of "Parallel modules", after the worktree cleanup succeeds. Do not leave the partners of a lower level to the host.

| Partner | When the opener archives |
|---|---|
| Build Fast, Architect consultation, Research Fast | After the lead verifies and integrates the result, before it returns the final evidence packet |
| Module Build Standard | After a successful `gmc wt rm`, as described in [step 6 of Parallel modules](#parallel-modules) |
| Review | After the host adopts the verdict. A Review session is not reused. When the target fingerprint changes, open a new Review |
| Research Deep, Ops | After the host uses the conclusion in the report |
| Build Standard | After the host accepts the final delivery state. For a task without a delivery, after the final result is accepted and included in the report |

The host's final report and the lead's final evidence packet each contain one line `已归档：<会话链接…>` (archived: session links). If no partner was archived, write `已归档：无`. The links use the Markdown format of "Single-layer Deep and Fast delegation". Partners that were kept are listed with their reason under "Partner archiving".

## Several goals in one window

If the user gives several independently deliverable goals, the host uses `lody_session_create_many` to open one Build Standard for each goal, and each one creates its own `gmc` worktree. For goals in the same repository, the host sets the merge order. A later goal starts delivery only after the earlier goal is merged, and it first syncs to the latest default branch and verifies again. The host combines all results into one report for the user.

## Parallel modules

Suppose investigation shows that a development goal splits into two or more modules, and each module needs its own investigation and implementation judgment. The lead Build Standard then hands the modules to module Build Standard sessions to develop in parallel. A small piece with a settled approach and acceptance conditions still goes to Build Fast. Every file has exactly one owning module. This includes lock files, generated files, and shared configuration. If this is not possible, do not split, or keep the shared part with the lead.

1. In its own worktree A, the lead first commits the interface skeleton that the modules share (types, signatures, stubs, or schema) as contract v1. The stubs must pass the build or checks of the repository. Commit them with `git commit -s` after the commit-time gates pass. When the split or the interface is uncertain, consult Architect as described in "Build Standard's development responsibility and design consultation" in SKILL.md. Write the split into the assignment of each module: the module, its unique write files, the interface and contract version, runtime coupling, and the acceptance commands.
2. Name each module `<goal short name>-<module>` to avoid name conflicts in the repository. Create the module worktrees after that commit with `gmc wt add <module name>... -b <branch of A>`. Open one module Build Standard (an independent session) for each module with `lody_session_create_many` and an explicit `workContext`. The title is `[Build Standard] Module <name>: <task>`.
3. A module Build Standard writes only in its own worktree and only the files it owns. It can consult Architect and delegate to Build Fast. When it finishes, it stages the changes in the module worktree. It does not commit, push, deliver, or open a Build Standard. It reports an evidence packet and ends. If the interface must change or the work goes beyond the write scope, it ends the turn with the question as the result and changes nothing itself.
4. When the interface must change, the lead decides. With an empty staging area in A, the lead commits contract v2. Contract v2 changes only files that the lead owns. A stub in a module file is changed by that module to follow the new interface. Then continue the affected modules with `lody_session_chat`: run `git -C <module worktree> merge --ff-only <branch of A>` and verify again.
5. Before integration, confirm that `git -C <module worktree> diff --name-only` and `git -C <module worktree> ls-files --others --exclude-standard` both print nothing. Otherwise return the module to staging. In the integration order, the lead applies each module into A with `git -C <module worktree> diff --cached --binary HEAD | git apply --index --3way` and resolves conflicts. The default is one PR. Run `git reset --soft $(git merge-base <default branch> HEAD)` to combine the contract commit and the module changes into one staged change in A. When the modules depend on each other and each layer can be reviewed alone, use stacked PRs instead. Each layer has its own branch and worktree, and the matching modules are applied into that layer. In A, run the complete checks that the repository requires and the verification at the affected entrypoint. Then return the review target (the staging area, or the binary-diff fingerprint of each layer) and the evidence packet to the host as described in the previous section. Do not push first.
6. For the final fingerprint of A, the host opens a new Review session and completes the independent review packet. An Architect that took part in the split or the design, and the module authors, cannot act as the reviewer. For stacked PRs, review each layer first and then the whole. After the review passes, the host continues the lead to push and deliver under the repository's rules. The lead cleans up the module worktrees that it created. After the merge, remove each module worktree with `gmc wt rm` under the cleanup rules of the `gmc` skill. For a staged module, first confirm that its staged changes are contained in the merged PR. Report the retained paths, the reasons, and the owners. After `gmc wt rm` succeeds, the lead archives the matching module session as described in [Partner archiving](#partner-archiving). If the cleanup does not succeed, keep the module session and state the reason.
