# Token Factory PPT and Website v1 Outline

> 状态：v1 讨论稿
> 目标：为市场团队准备 Token Factory 销售版 PPT 和全新官网的素材大纲。
> 边界：本文先收敛叙事、用户画像、内容模块和待补素材，不直接产出最终 PPT 页稿或官网文案。

## 1. 命名约定

- 统一产品名称：Token Factory
- 后续口头或草稿中出现 `tokenfactory`、`TokenFactory`、`token factory` 等写法，对外统一修正为 `Token Factory`。

## 2. 本次材料目标

本次优先输出两类市场素材的 v1 大纲：

- 销售拜访版 PPT：面向 B 类和 C 类讲清楚 Token Factory 的产品价值、商业化能力和采购理由。
- 全新官网：建立 Token Factory 的第一版官网信息架构和核心叙事。

当前重点不是泛泛介绍 Token API，而是讲清楚：

> Token Factory 是面向地方智算中心和大型企业的、GPU 资源变现与内部供给的 MaaS 操作系统。

这是当前可讨论的主张，不是最终定稿。

## 3. 用户画像

### A 类：Token 的真实使用者

A 类是最终消费模型能力的人。

- 可能直接调用 Token API。
- 也可能通过 OpenClaw 等 AI 应用间接使用模型服务。
- 他们关注可用性、速度、稳定性、价格和接入便利性。
- A 类不是当前销售材料的核心采购对象，但 A 类体验决定 C 类平台的流量、留存和口碑。

### B 类：企业内部 Token 使用方

B 类是企业组织内部使用 Token 的管理者和使用者。

- 关注员工、部门、项目的模型使用情况。
- 关注成本统计、费用归因、预算控制和消耗趋势。
- 关注企业内部 AI 应用接入、权限、安全、合规和效率。
- 需要 Dashboard 和 Copilot 帮助他们看清楚 Token 使用是否产生价值。

### C 类：Token Factory 的采购与运营主体

C 类是当前第一优先级客户，也是 Token Factory 当前最核心的采购对象。

- 第一优先级：地方智算中心。
- 其他可覆盖对象：大型企业、算力云、GPU 租赁平台、AI 云服务商、IDC 等。
- 他们拥有或管理 GPU 资源，需要把 GPU 资源转化为可供给、可计量、可运营、可治理的 Token API / MaaS 服务。
- MaaS 不是 ToC 专属概念。对地方智算中心，MaaS 第一场景通常是对外售卖；对大型企业，MaaS 第一场景通常是面向内部部门、员工和应用供给模型能力。

C 类内部至少拆成两种视角：

- 算力运维人员：关注 GPU 利用率、资源稳定性、模型负载、服务质量、推理效率、故障和容量。
- 算力运营人员：关注用户注册、流量增长、客户管理、订单转化、营销活动、收入和续费。
- 企业内部平台负责人：关注内部供给、部门分账、预算控制、合规审计、应用接入和持续服务质量。

### D 类：DaoCloud 与投资 / 战略叙事对象

D 类服务于 DaoCloud 自身的业务叙事。

- 面向投资人：证明 Token Factory 所在市场值得投资，DaoCloud 有技术和产品壁垒。
- 面向地方智算中心和大型企业决策层：证明买 Token Factory 不是买一个工具，而是获得一套可经营、可治理、可持续供给的 MaaS 系统。
- 面向 DaoCloud 内部：统一产品、市场、销售、交付和技术团队的表达口径。

## 4. 核心商业判断

Token Factory 的第一客户是 C 类，核心经营模式也必须围绕 C 类和 D 类成立。

但 C 类愿意采购的前提，不只是 Token Factory 自身技术先进，而是它能帮助 C 类服务好 A 类和 B 类。对地方智算中心，这通常体现为外部收入；对大型企业，这通常体现为内部 AI 能力供给、成本治理和组织效率。

因此材料需要同时回答四个问题：

- C 为什么要买：GPU 资源需要从“资产 / 成本”变成可运营、可治理、可衡量的 MaaS 供给能力。
- C 买了怎么产生价值：地方智算中心通过 Token API、企业客户、AI 应用生态和运营工具形成持续变现；大型企业通过内部供给、分账、预算、审计和应用接入形成组织效率与成本治理收益。
- B 为什么会用：企业内部可以统计、管理、控制和优化 Token 使用。
- DaoCloud 为什么能做：有 Kubernetes、推理加速、算力纳管、d.run 运营实践和产品化能力。

## 5. 面向 C 类的价值主线

### 5.1 技术先进性

DaoCloud 的技术可信度来自以下方向：

- 深耕 Kubernetes 多年，理解云原生基础设施和企业级平台工程。
- 是 vLLM 核心贡献者企业之一，具备推理服务工程化经验。
- 当前聚焦算力纳管和推理加速。
- Token Factory 本质上是推理服务的商业化平台。

对 C 类来说，推理技术的价值不是“技术炫技”，而是：

- 更高推理性能。
- 更低推理成本。
- 更稳定、可商用、可持续的推理服务质量。
- 更好的 GPU 利用率和资源调度效率。

后续需要补充的 DaoCloud 技术案例维度：

- 硬件适配：支持过哪些 GPU / NPU / 国产硬件 / 异构资源。
- 推理性能：吞吐、延迟、并发、冷启动、长上下文等对比数据。
- 成本优化：单位 Token 成本下降、GPU 利用率提升、资源碎片降低。
- 稳定性：SLA、故障恢复、弹性伸缩、限流熔断、多租户隔离。
- 工程化：Kubernetes 集成、模型服务生命周期、灰度发布、观测和运维。
- 真实案例：d.run 或客户场景中的部署规模、业务结果、问题解决前后对比。

### 5.2 MaaS 商业化能力

C 类最终不是只要模型推理能力，而是要把 Token 服务交付给 A 类和 B 类。这个交付可以是地方智算中心对外售卖，也可以是大型企业对内部组织供给。

因此 Token Factory 需要提供 MaaS 平台能力：

- Token API 服务。
- 用户管理。
- 企业 / 租户管理。
- 计量与计费。
- 套餐、价格、订单和账单。
- 配额、限流、权限和审计。
- 模型服务管理。
- 运营分析。
- 营销活动和客户增长工具。

DaoCloud 自己做过 d.run 算力平台，因此 Token Factory 不是纯概念产品，而是基于真实平台运营经验抽象出的产品能力。

## 6. Dashboard 内容方向

Dashboard 先按已有能力处理，但后续需要用产品原型和真实功能校准。

### 6.1 面向 B 类的企业使用 Dashboard

目标：帮助企业看清楚 Token 使用是否可控、是否有效、是否值得持续投入。

可包含内容：

- 总体消耗：Token 用量、调用次数、费用、趋势。
- 组织分析：按部门、团队、项目、员工统计使用情况。
- 模型分析：不同模型的调用量、成本、性能和错误率。
- 应用分析：OpenClaw 等 AI 应用消耗了多少 Token，带来哪些业务使用。
- 成本归因：按部门、项目、应用、API Key 分摊费用。
- 预算管理：预算额度、超额提醒、异常增长预警。
- 效率分析：高频场景、活跃用户、沉默用户、使用峰谷。
- 安全合规：API Key 使用、权限、审计日志、异常调用。
- 管理建议：哪些团队需要扩容，哪些使用存在浪费，哪些应用值得推广。

### 6.2 面向 C 类运维人员的资源 Dashboard

目标：帮助算力平台方保证 Token 服务稳定、低成本、高效率。

可包含内容：

- GPU 利用率、显存利用率、节点健康状态。
- 模型服务负载、并发、队列、吞吐和延迟。
- 单位 Token 成本、资源碎片、空闲资源。
- 服务质量：错误率、超时率、SLA、告警。
- 容量预测：资源紧张趋势、扩容建议、热点模型。
- 调度与弹性：模型副本、扩缩容、负载迁移。
- 多租户隔离：租户资源消耗、配额、限流和异常行为。

### 6.3 面向 C 类运营人员的业务 Dashboard

目标：帮助算力平台方和企业平台方把 GPU 资源变成持续增长或持续可治理的 MaaS 供给体系。

可包含内容：

- 用户注册、激活、留存、流失。
- 企业客户、个人开发者、渠道客户分布。
- 流量趋势、调用趋势、收入趋势。
- 订单、套餐、账单、续费、欠费。
- 客户分层：高价值客户、增长客户、风险客户。
- 模型热度：哪些模型带来收入，哪些模型消耗资源但转化差。
- 营销活动：优惠券、试用额度、活动转化、渠道效果。
- 收益分析：收入、毛利、资源成本、单位 Token 利润。

## 7. Copilot 内容方向

Copilot 先按已有能力处理，但后续需要结合原型确认真实交互边界。

Copilot 的定位：

> 用 Chat 作为入口，让 B 类和 C 类用户直接与 Token Factory 的数据、资源和运营系统对话。

### 7.1 面向 B 类的 Copilot

可支持的问题和动作：

- 查询本月 Token 消耗、费用和趋势。
- 查询某部门、某项目、某员工的使用情况。
- 分析费用上涨原因。
- 找出异常调用、浪费调用或高成本模型。
- 生成部门使用报告。
- 给出预算控制和模型选型建议。
- 解释某个 AI 应用为什么消耗增加。

### 7.2 面向 C 类运维人员的 Copilot

可支持的问题和动作：

- 查询当前 GPU 资源利用率和异常节点。
- 分析某个模型服务延迟升高的原因。
- 识别热点模型、资源瓶颈和容量风险。
- 汇总过去 24 小时的告警和故障。
- 给出扩容、缩容、迁移或限流建议。
- 生成运维日报和服务质量报告。

### 7.3 面向 C 类运营人员的 Copilot

可支持的问题和动作：

- 查询用户增长、调用增长和收入变化。
- 分析某类客户为什么转化下降。
- 找出高价值客户和潜在流失客户。
- 分析营销活动效果。
- 推荐套餐、折扣、试用额度和增长动作。
- 生成销售拜访摘要和客户经营建议。

## 8. 销售拜访版 PPT 初版结构

建议先控制在 12-15 页。

1. 封面：Token Factory
2. 一句话主张：GPU 资源变现与内部供给的 MaaS 操作系统
3. 地方智算中心的现实问题：有 GPU，不等于有可持续收入
4. 为什么只卖 GPU 不够：资源、模型、Token、客户和运营没有闭环
5. Token Factory 的答案：把 GPU 资源包装成可售卖或可内部供给的 Token API / MaaS 服务
6. 用户闭环：C 服务 B 和 A，DaoCloud 帮 C 建立平台能力
7. 技术底座：推理加速、算力纳管、Kubernetes、vLLM、稳定服务
8. MaaS 平台能力：用户、租户、模型、计量、计费、权限、订单
9. Dashboard：企业使用分析、资源运维分析、平台运营分析
10. Copilot：用 Chat 驱动统计、运维和运营分析
11. AI 应用生态：Token API 可被 OpenClaw 等应用消费
12. d.run 实践：DaoCloud 自身平台经验和可复用能力
13. 客户收益：更高资源利用率、更低服务成本、更强客户变现
14. 部署与合作模式：交付给地方智算中心，帮助其运营 MaaS 服务
15. 下一步：试点、技术验证、商业化共建

## 11. 当前已确认结论

- 产品统一名称为 Token Factory。
