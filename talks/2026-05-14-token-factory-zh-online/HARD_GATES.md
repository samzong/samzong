# Token Factory Hard Gates

本文是本次 Token Factory PPT 与官网素材整理、内容大纲、后续草稿制作的硬门禁。任何素材、观点、页面、章节、卖点，如果不能归类到用户定义的 A/B/C/D 类及其细分场景下，就先暂停，不进入正式大纲。

## Gate 1：所有内容必须回到 A/B/C/D

所有素材最终必须能明确归入以下对象之一：

- A 类：真正使用 Token 的终端用户。
- B 类：Token 使用企业内部的人、团队、部门或管理者，关注企业内部 Token 使用、统计、预算、治理、分析和效率。
- C 类：Token Factory 的采购与运营主体，当前第一优先级是地方智算中心；同时覆盖大型企业内部 MaaS / Token 供给平台。
- D 类：Token Factory 的开发方 DaoCloud 及其资本、投资、产品战略叙事视角，重点是让投资人投资 DaoCloud，让算力平台方购买产品与理念。

## Gate 2：当前 PPT 与官网优先服务 C，兼顾 B，支撑 D

本次 v1 目标不是泛泛介绍 Token Factory。

- PPT：先做销售拜访版本，主要面向 B 和 C 类，但真正第一客户是 C 类。
- 官网：讲清楚 Token Factory 的产品定位、能力、价值和可信度，服务 C 类采购决策，同时让 D 类看到增长逻辑。
- A 类只作为 C 类客户产生价值的下游使用场景，不喧宾夺主。
- B 类是 C 类买单后能形成价值的重要证明，尤其是大型企业内部使用和企业内部 MaaS 治理场景。
- D 类不是普通官网访问者，而是用于解释 DaoCloud 为什么值得投入、为什么能卖给 C、为什么这个方向有经营生命线。

## Gate 3：C 类不能被误写成纯 ToC MaaS

C 类客户包括：

- 地方智算中心：当前第一优先级，核心场景是 GPU 资源变现、对外供给、运营增长、客户获取、计费结算、SLA、安全、算电协同和经营回报。
- 大型企业平台方：建设内部 MaaS / Token 供给平台，核心场景是内部供给、部门预算、成本分摊、应用 / Agent 接入、SLA、容量、安全和治理。

禁止把 MaaS 只写成 ToC 或只写成“模型 API 商店”。Token Factory 背后是供给、经营、治理和持续运营系统。

## Gate 4：Dashboard / Copilot 素材必须分清使用者

Dashboard 归类时必须说明视角：

- B 视角：部门、应用、Agent、Copilot、预算、用量、Showback / Chargeback、企业内部统计分析。
- C 运维视角：GPU / NPU、模型服务、吞吐、延迟、KV Cache、队列、SLA、容量、稳定性、算电协同。
- C 运营视角：用户注册、租户、流量、套餐、收入、订单、客户、营销、经营闭环、毛利。
- C 财务 / FinOps 视角：单位 Token 成本、收入、毛利、预算、单机资产经营、回本期、ROI。
- D 视角：技术先进性、市场空间、可复制商业模式、DaoCloud 产品化能力、成功案例和投资价值。

Copilot 归类时必须说明它帮助谁：

- B：问企业内部统计、预算、费用消耗、部门/应用/Agent 使用情况。
- C 运维：问容量、资源池、SLA、队列、缓存、路由、故障根因。
- C 运营：问毛利、客户套餐、租户价值、经营闭环、分成方案、老板摘要。
- D：展示 DaoCloud 把复杂 Token Factory 运营系统智能化、产品化、可卖给平台方的能力。

## Gate 5：素材不是越多越好，必须服务销售叙事

进入 PPT / 官网前，每条素材必须回答至少一个问题：

- 它证明 C 为什么要买 Token Factory 吗？
- 它证明 C 买了之后怎么服务 A / B 并产生收入或内部价值吗？
- 它证明 DaoCloud 比别人更适合做这个产品吗？
- 它能支撑销售拜访时客户理解、相信、继续聊下一步吗？
- 它能支撑官网访客快速理解产品定位并产生联系意愿吗？

不能回答这些问题的素材，先放入素材库，不进入 v1 主线。

## Gate 6：表达要避免混淆

禁止混淆：

- A 的使用体验 和 B 的企业治理。
- B 的内部管理需求 和 C 的采购运营决策。
- C 的地方智算中心对外经营 和 C 的大型企业内部供给。
- C 的运维视角 和 C 的运营视角。
- Dashboard 的指标展示 和 Copilot 的自然语言分析入口。
- MaaS 的服务出口 和 Token Factory 的供给/经营/治理系统。
- DaoCloud 的技术能力 和客户最终得到的经营价值。

## Gate 7：所有强数字必须标注状态

用户已确认：当前 v1 讨论中，HTML 原型、内部研究、老板材料和推理优化 PPT 中的数字先作为真实素材使用，不再默认当作虚构示例处理。

工作方式：

- 销售拜访 PPT v1 可以直接使用这些数字讲产品价值。
- 素材文件内部仍保留来源，方便后续核验和替换。
- 正式对外发布官网或公开材料前，再补充是否可披露、是否可署名、是否需要匿名化。

## Gate 8：下一阶段制作顺序

制作 PPT / 官网大纲时，先按以下顺序过门禁：

1. 明确本页或本章节主要服务 A/B/C/D 哪一类。
2. 明确细分场景：地方智算中心、企业内部平台、企业员工/部门、运维、运营、财务、投资人等。
3. 明确素材来源：用户口述、老板 HTML、架构文档、Dashboard、Copilot、待补充案例。
4. 明确对销售拜访或官网转化的作用。
5. 再进入正式叙事和文案。

## Gate 9：用户已确认的 v1 约束

技术先进性：

- DaoCloud 技术案例优先来自 `推理优化PPTv0.1.0.pptx`。
- DaoCloud Kubernetes 贡献排名 Top3。
- DaoCloud vLLM 贡献排名 Top5。
- 推理优化、硬件适配、InferX、llm-d、vLLM、Kubernetes 能力是 Token Factory 技术先进性的核心支撑。

PPT 受众与比例：

- PPT 是销售拜访版本。
- 页数规划约 30 页，不低于 25 页。
- 听众通常是高层领导。
- 内容比重按 60% 地方智算中心、40% 大型企业组织；两类 C 场景都要有，在需要区分的地方明确说明。

官网方向：

- 官网使用统一入口，不拆多个站点入口。
- 官网结构优先包括：
  - 产品介绍。
  - 技术先进性。
  - 用户场景：地方智算中心和大型企业。

能力状态：

- Dashboard 能力按已有能力处理。
- Copilot 能力按已有能力处理。
- 不要把已经在老板 HTML 中出现的 Dashboard / Copilot 能力写成 Roadmap，除非用户后续明确修正。

## Gate 10：PPT 不是产品手册，必须是高层销售拜访叙事

销售拜访 PPT 的主要听众是高层领导，因此每一页都必须回答高层关心的问题，而不是堆功能细节。

每页进入 PPT 前必须能回答：

- 这一页要让客户相信什么？
- 这一页服务地方智算中心还是大型企业，或两者都服务？
- 这一页对应 A/B/C/D 哪类对象，其中 C 的视角是运营、运维、财务还是管理者？
- 这一页证明的是经营价值、技术可信度、产品能力、落地路径，还是合作模式？
- 这一页之后，销售希望客户愿意继续聊什么下一步？

禁止：

- 把 Dashboard、Copilot、MaaS、推理优化分别堆成孤立功能介绍。
- 长时间讲底层术语而不翻译成收入、成本、SLA、利用率、回本期、治理效率。
- 把高层销售拜访做成工程技术评审。
- 把 PPT 做成官网页面合集。

## Gate 11：PPT 主线必须先讲“为什么现在需要”，再讲“DaoCloud 怎么做”

销售 PPT 的叙事顺序必须优先围绕客户问题展开：

1. 现状矛盾：有 GPU / 模型 / 平台，不等于有可持续 Token 供给和经营闭环。
2. C 类客户痛点：
   - 地方智算中心：GPU 资产如何变现、如何获客、如何计量结算、如何保障 SLA、如何持续运营。
   - 大型企业平台方：内部 AI 能力如何供给、如何分账、如何预算、如何治理、如何保障关键业务。
3. Token Factory 定位：GPU 资源变现与内部供给的 MaaS 操作系统，背后是供给、经营、治理和持续优化系统。
4. 产品能力：MaaS 服务出口、Dashboard 经营驾驶、Copilot 智能工作台、管理后台、计量计费、租户治理、安全、算电协同。
5. 技术先进性：Kubernetes Top3、vLLM Top5、InferX、推理优化案例、异构硬件适配、生产级推理闭环。
6. 落地与经营模式：初装费、运维费、Token 分成；或大型企业内部供给、预算和治理闭环。
7. 下一步：样板项目、PoC、技术交流、经营测算、领导决策材料。

不能先从功能清单讲起。功能必须服务上述主线。

## Gate 12：地方智算中心与大型企业必须同时出现，但权重不同

销售 PPT 的整体权重为 60% 地方智算中心、40% 大型企业。

使用规则：

- 共性页可以统一讲 Token Factory 的产品定位、技术底座、Dashboard、Copilot、MaaS、推理优化。
- 只要涉及经营模式、价值指标、客户路径、治理对象，就必须区分地方智算中心与大型企业。
- 地方智算中心优先讲收入、客户、套餐、计费结算、毛利、资产回本、算电协同和区域运营。
- 大型企业优先讲内部供给、部门预算、Showback / Chargeback、应用 / Agent 接入、SLA、合规、安全和关键业务保障。
- 不允许只讲地方智算中心后把大型企业一笔带过。
- 不允许为了覆盖大型企业而削弱地方智算中心第一优先级。

## Gate 13：官网是统一入口，但必须让两类 C 都看见自己

官网不拆多个入口，但首页和核心模块必须同时照顾两类 C：

- 地方智算中心：看到 GPU 资源变现、MaaS 经营、客户服务、计量计费、运营增长和资产回报。
- 大型企业平台方：看到内部 MaaS、统一模型供给、部门治理、预算分摊、应用 / Agent 接入和安全合规。

官网结构优先围绕三件事：

1. 产品介绍：Token Factory 是什么，解决什么经营问题。
2. 技术先进性：为什么 DaoCloud 能做，Kubernetes + vLLM + InferX + 真实优化案例。
3. 用户场景：地方智算中心和大型企业两条场景线。

官网禁止：

- 首页只像 ToC 模型 API 商店。
- 首页只讲技术，不讲客户经营结果。
- 把地方智算中心和大型企业做成两个割裂产品。
- 把 Dashboard / Copilot 写成未来愿景；当前按已有能力表达。

## Gate 14：素材进入正式内容前必须形成“对象-场景-证据”三元组

任何素材进入 PPT 或官网前，必须先写清楚：

- 对象：A/B/C/D，以及更细的角色。
- 场景：地方智算中心对外经营、大型企业内部供给、企业员工使用、C 运维、C 运营、C 财务、D 投资叙事等。
- 证据：老板 HTML、Dashboard 素材、Copilot 素材、推理优化 PPT、用户口述、真实案例、内部测算。

例子：

- “H20 & R6KD TTFT ↓97%”不能单独出现；必须归到 C 运维 / 地方智算中心异构硬件生产化，并说明它证明 DaoCloud 能把异构硬件转化为可达 SLO 的 Token 产能。
- “客服中心 Copilot 节省人工成本 ¥180K/月”不能单独出现；必须归到 B 企业内部价值证明，并说明它帮助 C 类大型企业平台方证明内部 MaaS 的业务价值。
- “星辰科技套餐消耗率 92%”不能单独出现；必须归到 C 运营 / 地方智算中心客户运营，并说明它证明 Token Factory 能支持套餐升级与收入增长。

## Gate 15：技术先进性必须转译成经营结果

技术材料可以保留，但必须转译。

技术表达与经营表达的映射：

- Kubernetes 调度 / 资源池化 / 队列 / 容错 → 更高资源利用率、更稳 SLA、更少人工运维。
- vLLM / SGLang / llm-d / PD 分离 → 更高吞吐、更低延迟、更低单位 Token 成本。
- KV Cache / Offload / event-aware routing → 长上下文和 Agent 场景成本下降、响应更稳定。
- AI 网关 → 模型服务可治理、可授权、可审计、可降级、可计量。
- Planner / well-lit path → 模型 + 硬件 + SLO 的可复制交付路径。
- 可观测闭环 → 从看见问题到自动优化回写，不只是监控。
- 异构硬件适配 → 地方智算中心和大型企业已有资产可被纳管、优化和经营。

如果某个技术点不能转译成收入、成本、SLA、利用率、回本期、安全、治理效率或交付可复制性，就不进入 v1 主线。

## Gate 16：最终交付物必须分阶段推进，不一次性越界

用户要求一步步推进，因此后续工作顺序必须保持：

1. 先做 PPT 大纲和内容草稿。
2. 用户确认主线后，再细化每页内容。
3. PPT 主线稳定后，再抽象官网信息架构。
4. 官网信息架构确认后，再写官网首版文案。
5. 不在未确认主线前直接生成最终 PPT、完整官网或视觉设计。

每一阶段结束都要回到 hard gate 检查：

- 是否服务 C 类第一客户。
- 是否保留 60% 地方智算中心 / 40% 大型企业。
- 是否用 B/A 证明 C 买了之后能产生价值。
- 是否用 D 证明 DaoCloud 值得被投资和被平台方采购。
- 是否避免 ToC MaaS、功能堆砌和技术堆料。
