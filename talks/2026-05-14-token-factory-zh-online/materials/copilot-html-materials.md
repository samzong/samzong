# Token Factory Copilot HTML 素材封存

来源：`token-factory/copilot/copilot-mockup.html`

用途：封存老板 HTML 原型里的 Copilot 能力、交互形态、对话场景、示例数据、右侧工作上下文和动作边界。本文不保留 CSS / DOM / JS 实现细节，只保留后续 PPT、官网、销售话术、产品讨论真正可复用的内容。

## 一句话定位

Copilot 在老板原型里不是普通聊天机器人，而是 `DaoCloud Token Factory 智能工作台`：面向 Token 供给、经营分析、容量规划、SLA 治理、成本归因、路由建议和多入口协同的智能控制中枢。

原型首页核心表达：

> 面向 Token 供给与运营的智能控制中枢，让资源、模型、流量、调度与经营持续协同运转。

> MaaS 是服务出口，Token Factory 负责背后的供给与经营系统。

## 产品边界

HTML 原型明确给出 Copilot 的执行边界：

> Copilot 负责分析、解释、建议、生成草案。高风险的结构性配置变更不直接在这里执行，而是引导到管理后台完成。

这句话非常重要，后续 PPT/官网应避免把 Copilot 讲成“随便一句话就自动改生产配置”。更准确的表达是：

- Copilot 负责理解上下文、归因、规划、生成方案、生成报告、给出建议。
- Dashboard / MaaS / 管理后台负责进一步查看、售卖、执行和审计。
- 高风险动作需要显式跳转后台，由平台团队确认执行。

- 成本上涨来自模型本身，还是服务模板与资源池组合？
- 如果目标是提升 ROI，是否应该调整模型路由？

## 场景 1：企业年度 Token 供给计划

定位：

- 企业型客户。
- 持续供给。
- 年度计划。
- SLA 承诺。

线程说明：

> 当前会话面向企业型客户，目标是把年度 Token 需求拆成可承诺、可交付、可控成本的持续供给方案，而不是单次平台交付。

用户问题：

> 某企业客户预计明年需要 18 亿 Token，我们应该怎么拆成供给计划、SLA 承诺和成本边界？

Copilot 结论：

- 这类客户买的不是一套复杂平台，也不是一次性交付，而是可持续、可预期、可控成本的 Token 供给结果。
- 应先定义年度需求、月度波峰、SLA 边界与成本带宽，再决定底层资源如何承接。
- 建议把 18 亿 Token 拆成基础供给包 + 峰值弹性包 + 高优先级保障包。
- 目标是在客户不自建重底座的前提下获得稳定供给，同时把容量与成本风险留在供给侧管理。

分析卡：

| 维度 | 内容 |
|---|---|
| 年度需求 | 18 亿 Token，按季度滚动校准，避免一次性锁死全年假设 |
| SLA 承诺 | 99.9% / 高优先级保障，核心业务走更高优先级路由与资源池 |
| 供给结构 | 基础包 + 弹性包 + 峰值保护，把持续供给和峰值波动拆开管理 |
| 成本边界 | 按年承诺、按月校准，用滚动校准降低供给侧成本偏差风险 |

建议输出步骤：

1. 拆出年度与月度需求：把年需求拆成基础供给、弹性波峰和高优先级承诺。
2. 定义成本与 SLA 边界：确认哪些能力进入承诺，哪些能力进入弹性或附加项。
3. 生成客户可读方案：输出供给摘要、SLA 承诺和成本测算草案。
4. 联动经营与交付：衔接销售报价、交付评估与持续供给看板。

- 生成供给方案。

## 场景 2：运营项目分成与结算设计

定位：

- 运营型客户。
- 经营闭环。
- 分成结算。
- 样板项目。

线程说明：

> 当前会话面向运营型客户，目标是判断资源是否已形成经营闭环，并设计初装费、运维费与 Token 分成的组合结构。

用户问题：

> 某地方平台已经有 GPU 和客户资源，我们怎样判断它是否形成经营闭环，并设计初装费、运维费和 Token 分成？

Copilot 结论：

- 资源本身不等于业务。
- 关键不是“有没有 GPU”，而是资源是否已经被组织成可供给、可计量、可结算、可滚动经营的闭环。
- 如果没有稳定需求、计量口径、结算对象和运营责任，项目就仍停留在“有资源、没模式”阶段。
- 更合理的结构是：前期初装费覆盖项目建设，中期运维费覆盖持续承接，后期按 Token 供给与经营结果分成。

分析卡：

| 维度 | 内容 |
|---|---|
| 资源状态 | 有资源，但闭环未完成 |
| 关键缺口 | 计量、结算、客户承接 |
| 商业结构 | 初装费 + 运维费 + Token 分成 |
| 下一步 | 先做样板闭环 |

样板路径：

1. 判断资源是否进入经营体系：确认真实需求、客户承接主体与持续供给对象。
2. 设计计量与结算口径：统一 Token 计量、费用拆分与分成对象。
3. 输出商业结构草案：生成初装费、运维费与分成比例的组合建议。
4. 形成可复制样板：把单点项目沉淀为后续可讲、可卖、可复用的运营案例。

## 场景 3：毛利被压缩的原因分析

定位：

- 网页工作台。
- 经营分析。
- research-lab。
- DeepSeek-R1。
- cn-prod-a / pool-a100-prod。
- 最近 24 小时。

线程说明：

> 当前会话聚焦 research-lab、DeepSeek-R1、cn-prod-a / pool-a100-prod 与最近 24 小时的经营表现，Copilot 已完成第一轮归因并给出经营分析方案。

用户问题：

> 今天毛利变差，主要是模型成本、租户结构，还是缓存命中率变化导致的？请按影响大小排序。

Copilot 结论：

- 毛利下滑不是单一指标恶化，而是三类因素叠加。
- 第一是 DeepSeek-R1 高成本路径占比上升。
- 第二是 research-lab 租户流量挤占高优先级推理容量。
- 第三是 KV Cache 命中率从 78% 降到 72%，导致单位 Token 成本被进一步放大。
- 有效吞吐达到 18.4M Token/分钟，但提升来自高成本模型服务组合，不是更优产能结构。
- 系统“更忙了”，但没有同步转成更好的毛利率，当前毛利率 34.7%。

分析卡：

| 影响排序 | 内容 |
|---|---|
| 1. 模型成本结构变化 | DeepSeek-R1 / latency-priority / pool-a100-prod 成本抬升最明显，单位 Token 成本 ¥1.82 / 1M |
| 2. 租户结构变化 | research-lab 流量激增，侵蚀高价值 GPU 产能，但收入增幅低于占用增幅 |
| 3. 缓存命中率下降 | 缓存命中下降直接推高 TTFT 和队列深度，队列峰值 184 |
| 相关对象 | DeepSeek-R1 / GLM-4.5 / pool-a100-prod，影响 cn-prod-a、research-lab、research-agents 工作区预算 |

模型成本占比：

| 模型 | 成本占比 |
|---|---:|
| DeepSeek-R1 | 41% |
| GLM-4.5 | 24% |
| Kimi-2.5 | 18% |
| MiniMax-M1 | 17% |

经营分析方案：

1. 识别异常与影响面：锁定毛利率、单位 Token 成本、有效吞吐、队列与缓存命中率的偏移窗口。
2. 归因到模型 / 租户 / 资源池 / 缓存 / 路由：已确认 research-lab 与 DeepSeek-R1 / pool-a100-prod 是主要压力组合。
3. 生成建议与备选方案：准备比较 GLM-4.5 替代路由、预算保护和缓存优化方案。
4. 导出报告或跳转后台执行：生成经营分析报告后，再去管理后台做显式策略调整。

## 场景 5：OpenClaw 异常根因分析

定位：

- Agent 通道。
- OpenClaw。
- DeepSeek-R1。
- 严重程度高。

线程说明：

> 当前会话由 Agent 通道发起，目标是返回可直接给 OpenClaw / workflow agent 使用的根因结论与缓解建议。

用户问题：

> OpenClaw 请求：请给出异常根因摘要和缓解建议。

Copilot 结论：

- 异常窗口为 19:42 到 20:05。
- 根因是 KV Cache 复用下降 + pool-a100-prod 队列积压 + research-lab 高峰流量突增共同触发。
- 影响表现为 TTFT 抬升、队列深度上冲到 184，并在 DeepSeek-R1 latency-priority 路径上放大 SLA 抖动。
- 缓解建议：先把低业务价值流量切向 GLM-4.5 balanced 路由，启用缓存保护策略，然后再对高优先级路由进行限流。
- 如需结构性策略调整，转到管理后台执行。

分析卡：

- Copilot 可以讲成算力运营助手。
- 运营人员可问毛利、客户套餐、租户结构、经营闭环、分成方案、套餐升级、老板摘要。
- 运维人员可问容量、资源池、SLA、队列、缓存、模型路由、异常根因和高峰保护。
- 它帮助 C 类客户把 GPU 资源运营成持续收入，而不只是上线模型服务。

面向 C 类大型企业平台方：

- Copilot 可以讲成内部 MaaS / Token 供给平台的智能运营入口。
- 重点不是 ToC 售卖，而是把内部供给、预算、SLA、部门成本和容量保护讲清楚。
